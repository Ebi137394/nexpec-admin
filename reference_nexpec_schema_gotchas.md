Authoritative NEXPEC schema facts (verified 2026-05-29 against migrations + the assign-inspector edge function). Check these before writing SQL that touches jobs/orgs/assets.

- **The inspector assigned to a job = `jobs.contractor_id`.** Set by the authorized dispatch path `supabase/functions/assign-inspector-to-job.sql` (`UPDATE jobs SET contractor_id = p_inspector_id`). `jobs.inspector_id` and `jobs.hired_inspector_id` also exist but are NOT the job-assignment column. **`jobs.assigned_inspector_id` does NOT exist** — despite `MOBILE_SYNC_LEDGER.md`'s Golden-Rule text calling it that (the ledger is wrong on the exact name). I assumed `inspector_id`/`assigned_inspector_id` twice and both were wrong; use `contractor_id`.
- **Latent `assigned_inspector_id` bug across migrations** → function bodies referencing it error at call time. Fixed: `global_search` (hotfix `20260706120000_global_search_contractor_id_fix.sql`). STILL to audit/fix (likely broken RPCs): `20260518170000_reviews_and_ratings`, `20260518160000_conversations_and_messages_v2`, `20260518180000_client_documents`, `20260518200000_bulletproof_reviews_docs_notifications_disputes`. Replace with `contractor_id`.
- **`public.assets` already exists** in the production DB (NOT in tracked migrations) — a `CREATE TABLE IF NOT EXISTS public.assets` silently no-ops and any policy referencing new columns (e.g. `org_id`) then fails with 42703. New asset tables must use a distinct name; the predictive-integrity feature uses **`public.inspection_assets`**.
- RLS helpers: **`public.nx_is_admin()`** (no-arg; also an overload `nx_is_admin(p_uid uuid)`) and **`public.is_member_of_org(p_org_id uuid)`**. Org-scoped tables use an **`org_id`** column. `public.organizations` PK is `id`.
- **`platform_fee_cents` is on `invoices`, NOT on `jobs`** (verified 2026-05-31 across all migrations: only ever `i.platform_fee_cents` in evidence-pack RPCs). `jobs` has the GENERATED, admin-only **`platform_spread_cents` = client_price_cents − inspector_payout_cents** — never expose it to client (leaks inspector payout, GR2) OR inspector (leaks client price). Two web routes selected `jobs.platform_fee_cents` → 500'd (non-existent column): `apps/web/.../inspector/wallet/statement/[period]/route.ts` + `client/finance/invoice/[jobId]/route.ts`. FIXED by removing it (client invoice shows only client_price; inspector statement shows only their payout = their net).
- **`jobs.payout_status` CHECK = `('unpaid','processing','paid','disputed')`** (baseline_core_tables:254-256). **`'released'` is NOT valid** and never was — code filtering `payout_status IN ('released','paid')` (statement route) or trigger branches checking `'released'` (god_mode_notifications) are dead/never-match. Terminal settled state is `'paid'`. FIXED the statement filter → `['paid']`.
- **Money = integer USD cents, platform-wide.** Canonical mobile formatter `src/core/utils/money.ts` (`formatUsd`/`toCents`/`fromCents`) is now byte-identical to web's `formatInvoiceCents` (apps/web/src/lib/data/invoices.ts:410) — empirically verified across the full value range; `formatUsd` default is 2 fraction digits. Web canonical money tables: `invoices.*_cents` + `jobs.*_cents` + `profiles.balance_cents`. Mobile legacy `inspector_earnings.*_halalas` / `wallets`(dollars) / `transactions` are off-canonical (see [[project-financial-security-crisis]]).
- **`inspection_reports` has NO `reviewer_id`/`reviewer_note`/`reviewed_at`** (verified 2026-06-23 against baseline 23076). Real approval columns: `status`, `is_published`, `is_client_approved`, `technical_approved[_by/_at]`, `financial_approved[_by/_at]`. The `approve_inspection_report(p_job_id,p_approved,p_comment)` RPC wrote all three phantom columns → client "Review & Pay → Confirm Release" crashed 42703 (column reviewer_id…does not exist); had NEVER worked. Fixed (migration 20260801162000): real columns + SECURITY DEFINER (self-authorizes caller=job client_id/agency_id). 
- **`job_events` is `event_type`/`metadata`, NOT `kind`/`payload`** (baseline 23484), and `event_type` CHECK = `('created','status_change','contractor_assigned','contractor_unassigned','soft_deleted','restored','application_created','application_status_change','fraud_alert')` — `'report_approved'` etc. are NOT valid. The same RPC inserted `kind`/`payload` + `'report_approved'` (double phantom). Use `event_type='status_change'` + put detail in `metadata` jsonb. (Distinct from `audit_events`, which the Stripe webhooks use.)
- **`profiles` has NO `is_active` and NO `is_featured`** (verified 2026-06-24 vs baseline CREATE TABLE). Live-account gate = **`status`** (CHECK `active`/`suspended`). Integer experience col = **`experience_years`** (`years_of_experience` is **text**). The baseline `get_marketplace_inspectors` + `search_inspectors` reference `p.is_active`/`p.is_featured`/`p.years_experience` — ALL PHANTOM; they only created because **plpgsql defers column resolution to call time**, whereas a VIEW or `LANGUAGE sql` fn validates immediately and 42703s (this broke the teaser `public_supply_feed` push; fixed → `status`/`public_listing_featured`/`experience_years`, commit 3327585). `jobs.is_featured` exists but is a different table. Teaser feed adds `profiles.public_listing_opt_in` + `public_listing_featured` (migration 20260801170000). **Lesson: never trust a plpgsql function body as proof a column exists — verify against CREATE TABLE + ALTERs.** See [[project_teaser_marketplace]].
- `pi_report_seals` columns: `root_sha256`, `items_root_sha256`, `captures_root_sha256`, `report_meta_sha256`, `chain_verified`, `items_count`, `captures_count`, `inspector_sealed_at`, `inspector_id` (= profiles.id), `job_id`, `report_id`. See [[project-ai-strategy]].
- **Evidence Vault (`client_documents`) — NOT dormant (CORRECTED 2026-06-25).** The full live column set (verified against the baseline CREATE TABLE) = `id, owner_id, job_id, kind` (enum drawing/spec_sheet/nda/prior_report/regulatory/vendor_doc/photo_evidence/other), `label, file_path, external_url, notes, created_at, updated_at, category, valid_from, valid_until, is_verified, verified_by, verified_at, is_archived`. The web vault (`apps/web/src/lib/data/vault.ts`) projects `category/valid_from/valid_until/is_verified/verified_by/verified_at/is_archived` + a `VaultCategory` enum — **these columns DO EXIST**, so the vault is NOT schema-blocked. The earlier "no migration adds them → dormant" claim was WRONG: it searched migrations only and missed the baseline dump (cols were added directly to remote and captured in baseline). Mobile screens `app/(admin)/vault/index.tsx` + `[id].tsx` exist but may still be UNWIRED (no dashboard NavCard) — that's a UI gap, not a schema gap. RLS `cdocs_admin_all` + storage bucket `client_documents` exist. **Lesson: verify against the BASELINE dump (`00000000000000_remote_baseline.sql` CREATE TABLE), not just later migrations — remote-applied columns only live in the baseline.** See [[project-cross-platform-parity]].
- **Leftover `USING(true)` "for testing" policies in the baseline = silent allow-all leaks.** `CREATE POLICY "Allow all access to messages for testing" ON public.messages USING(true)` (no FOR clause → ALL commands, all roles) let ANY authenticated user read/write EVERY chat message — nullified all client↔admin/inspector↔admin silos. Caught by the rls_team_workspace pgTAP suite; DROPPED in migration **20260801192000** (PENDING db push). **Sweep findings — ALL FIXED (migration 20260801196000, commit af0a220, PENDING db push):** `payment_methods` had `FOR SELECT/UPDATE/DELETE USING(true)` (any user read/modify/delete ANY card) → dropped, owner-scoped + anon revoked; **`work_orders` had RLS DISABLED entirely + GRANT ALL anon + 8 USING(true) policies (fully public)** → RLS ENABLED + owner/admin scoped + anon revoked; `legal_consents` `USING(true)` read leak (ip/geo/UA PII) → dropped, owner+admin read only, anon read revoked (anon INSERT kept for pre-auth capture). Locked by pgTAP `supabase/tests/rls_financial_pii_test.sql` (deny-matrix, plan 14). **CI gate: `.github/workflows/db-tests.yml`** boots a throwaway Supabase stack + runs `supabase test db` on every PR touching `supabase/**` → any future USING(true)/silo/financial-PII regression fails the build (commit 536504a). Caveat: **`work_orders.status` DEFAULT 'open' is NOT in its CHECK** (active/pending/in_progress/completed/cancelled) → bare inserts fail; always set an explicit valid status. Reference tables with USING(true) (country_codes, fx_rates, inspection_domains, inspector_skills, review_weights_config) are fine. **Write-side twin (also dropped, migration 20260801194000):** `insert_chat_msgs` FOR INSERT WITH CHECK (auth.uid()=sender_id) — no party/role check → any user could post to ANY conversation; the scoped `msg_insert_party` (+ team `msg_team_insert`) cover legit posting. So BOTH loose messages policies are now gone; silos enforced for read AND write. **Also: never `LIKE` a Postgres ENUM** — `conversation_kind LIKE 'job_%inspector%'` → "operator does not exist: conversation_kind ~~ unknown" (was swallowed by tg_notify_messages' EXCEPTION guard → silent notify failures); use enum equality (`= 'job_inspector_admin'::conversation_kind`) or `::text LIKE`. **Lesson: grep the baseline for `USING (true)` on non-reference tables — each is a candidate leak; pgTAP RLS deny-matrices catch them.**
- **Supabase default privileges auto-grant new public-schema TABLES to `anon`+`authenticated`** (verified 2026-06-24: teaser projection table 182000 self-test caught `anon` holding INSERT). `REVOKE ALL … FROM PUBLIC` does NOT remove those role-specific grants. For a public READ-ONLY table: `REVOKE ALL ON t FROM PUBLIC, anon, authenticated;` then `GRANT SELECT ON t TO anon, authenticated, service_role;`. (Views are mostly non-updatable so this bit only when feeds graduated views→tables.) A SECURITY DEFINER refresh fn owned by postgres still writes (owner bypasses the grant).
